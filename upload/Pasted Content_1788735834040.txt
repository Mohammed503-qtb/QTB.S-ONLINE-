# 1. الصورة الكاملة للنظام
 
المنظومة تتكون من 5 أجزاء مترابطة:
 
**تطبيق العميل** → تصفح المنتجات → البحث والفلاتر → السلة → العنوان → الشحن → الدفع → رفع/تسجيل عملية التحويل → متابعة الطلب → التواصل عبر واتساب → الاستبدال والإرجاع → الحساب الشخصي
 
**نظام الإدارة** → المنتجات → التصنيفات → المخزون → الأسعار والخصومات → الطلبات → العملاء → المدفوعات → الحسابات البنكية → الشحن → المرتجعات → التقارير → المحتوى → الإشعارات → إعدادات التطبيق → التحكم في الإصدارات → إيقاف/تشغيل أجزاء من النظام
 
**محرك الطلبات** → ينشئ رقم طلب → ينشئ كود تتبع → يحدد حالة الطلب → يربط الطلب بالعميل والدفع والشحن والمخزون → يمنع التلاعب أو التكرار
 
**محرك الحسابات والمخزون** → المبيعات → المشتريات → المصروفات → التحويلات → الحسابات البنكية → الصندوق → المخزون → الأرباح → المبالغ المستحقة → المرتجعات
 
**طبقة التحكم المركزية** → هل التطبيق مفتوح؟ → هل الإصدار الحالي مسموح؟ → ما الحد الأدنى للإصدار؟ → هل يوجد صيانة؟ → هل التسجيل مفتوح؟ → هل الدفع البنكي مفتوح؟ → هل الشحن مفتوح؟ → أي أقسام تظهر؟ → أي محتوى يعرض؟
  
# 2. أهم فكرة في المشروع
 
أنت قلت نقطة مهمة جدًا:
 
 
قاعدة البيانات مجانية ومحدودة السعة وأريد أن أتحكم بكل شيء من داخل التطبيق.
 
 
هنا لا أنصح أبدًا بأن تجعل تطبيق العميل يتعامل مباشرة مع صلاحيات إدارة قاعدة البيانات.
 
الصحيح:
 `تطبيق العميل       ↓ Backend / API       ↓ Database ` 
وبجانبهم:
 `تطبيق الإدارة       ↓ Admin API       ↓ Database ` 
وبذلك حتى لو كانت قاعدة البيانات محدودة، أنت تستطيع التحكم من لوحة الإدارة في:
 
 
- حذف البيانات القديمة
 
- أرشفة الطلبات
 
- تنظيف السجلات
 
- ضغط المحتوى
 
- حذف الصور غير المستخدمة
 
- إدارة المستخدمين
 
- إدارة الجداول
 
- النسخ الاحتياطية
 
- تصدير البيانات
 
- مراقبة استهلاك المساحة
 

 
والأهم:
 
**لا يتم وضع مفتاح المدير أو صلاحيات قاعدة البيانات الحساسة داخل تطبيق العميل.**
  
# 3. شكل التطبيق
 
أقترح Flutter لكي يكون نفس المشروع قادرًا على إنتاج:
 `Android iPhone ` 
والتطبيق نفسه يحتوي على أكثر من تجربة حسب الدور.
 
عند تشغيل التطبيق:
 `Splash    ↓ Remote Configuration    ↓ Version Check    ↓ Maintenance Check    ↓ Authentication    ↓ Role Detection    ↓ فتح الواجهة المناسبة ` 
والأدوار مثل:
 `CUSTOMER ADMIN MANAGER OPERATOR ACCOUNTANT WAREHOUSE DELIVERY CONTENT_MANAGER ` 
لكن يمكن بدء المشروع بعدد أدوار أقل ثم توسيعه.

- الأكثر مبيعًا

# 5. صفحة المنتج
 
كل منتج يجب أن يكون كيانًا متكاملًا.
 
المنتج يحتوي على:
 
 
- اسم
 
- وصف
 
- صور
 
- فيديو اختياري
 
- السعر
 
- سعر قبل الخصم
 
- نسبة الخصم
 
- SKU
 
- باركود
 
- التصنيف
 
- الماركة
 
- الألوان
 
- المقاسات
 
- الكمية
 
- حالة التوفر
 
- الحد الأدنى للمخزون
 
- الوزن
 
- خيارات إضافية
 
- صور لكل لون
 
- صور لكل مقاس
 
- حالة المنتج
 
- ترتيب الظهور
 

 
مثلاً الملابس:
 `قميص  الألوان: أسود أبيض أزرق  المقاسات: S M L XL XXL ` 
ولا يصح أن يكون المخزون:
 `قميص = 20 `

 `Black / M = 4 Black / L = 6 White / M = 3 White / L = 7 ` 
وهكذا.
  
# 6. السلة
 
العميل يضيف المنتجات.
 
كل سطر في السلة يحتوي:
 `المنتج Variant الكمية السعر الخصم الإجمالي ` 
ثم:
 `الإجمالي الفرعي الخصومات الشحن الضريبة إن وجدت الإجمالي النهائي ` 
مع إعادة التحقق من المخزون قبل تأكيد الطلب.
 
وهذا مهم جدًا لأن منتجًا ما قد ينفذ بينما العميل ما زال في السلة.
  
# 7. تسجيل الدخول
 
يمكن تصميمه عبر:
 
 
- رقم الهاتف
 
- OTP
 
- حساب ضيف
 
- Google/Apple لاحقًا إن احتجت
 

 
والعميل لديه:
 `الملف الشخصي العناوين الطلبات المفضلة الإشعارات الاستبدال والإرجاع طرق التواصل `  
# 8. العناوين داخل اليمن
 
لا تجعل العنوان مجرد نص.
 
يجب أن يكون:
 `المحافظة المدينة المديرية الحي الشارع اسم نقطة مشهورة رقم الهاتف ملاحظات الموقع الجغرافي اختياري ` 
مثلاً:
 `عدن المنصورة ... بجوار ... ` 
وهكذا تستطيع الإدارة حساب الشحن حسب المنطقة.
  
# 9. محرك الشحن
 
الإدارة تحدد:
 `المحافظة المدينة المنطقة تكلفة الشحن الحد الأدنى الحد الأقصى مدة التوصيل ` 
وقد يكون هناك:
 `استلام من المتجر = 0 داخل المنطقة = 1000 منطقة أخرى = 1500 ... ` 
والقيمة لا يكتبها العميل يدويًا.
 
التطبيق يحسبها حسب عنوانه.
  
# 10. الدفع البنكي — الجزء الذي طلبته
 
هذا من أهم أجزاء النظام.
 
الإدارة تضيف الحسابات البنكية والمحافظ ووسائل التحويل.
 
مثلاً:
 `بنك اسم المستفيد رقم الحساب رقم الآيبان إن وجد رقم المحفظة رقم الجوال اسم البنك تعليمات التحويل ` 
والعميل عند اختيار الدفع:
 `الدفع بالتحويل البنكي ` 
تظهر له الحسابات المتاحة.
 
مثلاً:
 `البنك: XXXXX اسم المستفيد: XXXXX رقم الحساب: XXXXX  [ نسخ رقم الحساب ]  أرسل المبلغ: 25,000 ريال ` 
ثم يتم إنشاء:
 
**Payment Reference Code**
 
مثلاً:
 `YM-7K4P29 `  
# 11. كود التتبع وكود الدفع
 
هنا أنصح ألا يكون هناك كود واحد فقط.
 
نستخدم:
 
### رقم الطلب
 `ORD-20260906-000125 ` 
### كود الدفع
 `PAY-7K4P29 ` 
### كود تتبع الطلب
 `TRK-9X82LM ` 
والعميل يضع **كود الدفع** في ملاحظات التحويل:
 `PAY-7K4P29 ` 
وهو ما يسمح للإدارة بربط التحويل بالطلب.
  
# 12. كيف تتم عملية الدفع
 
التدفق:
 `العميل يؤكد الطلب         ↓ النظام ينشئ الطلب         ↓ يحسب الإجمالي         ↓ يولد Payment Code         ↓ يعرض الحساب البنكي         ↓ العميل يحول المبلغ         ↓ العميل يسجل عملية الدفع ` 
يسجل:
 `رقم العملية المبلغ البنك المستخدم تاريخ التحويل اسم المحول كود الدفع صورة الإيصال ملاحظات ` 
ثم:
 `Pending Verification `  
# 13. التحقق من الدفع
 
الإدارة ترى:
 `Payments Queue ` 
مثلاً:
 `PAY-7K4P29 Order: ORD-... Amount: 25,000 Bank: ... Customer: ... Receipt: image ` 
وتوجد:
 `قبول رفض طلب تحقق إضافي ` 
عند القبول:
 `Payment Verified ` 
ويتحول الطلب إلى:
 `Confirmed ` 
وعند الرفض:
 `Payment Rejected ` 
مع سبب الرفض.
  
# 14. الحالات المهمة في الدفع
 
لا تكتفِ بـ:
 `مدفوع / غير مدفوع ` 
بل:
 `UNPAID PAYMENT_SUBMITTED UNDER_REVIEW VERIFIED PARTIALLY_PAID REJECTED EXPIRED REFUNDED PARTIALLY_REFUNDED ` 
وهذا يمنع مشاكل الحسابات.
  
# 15. ماذا لو دفع العميل مرتين؟
 
النظام يجب أن يكتشف:
 `Order X Payment A Payment B ` 
ويظهر:
 `Possible Duplicate Payment ` 
وتقرر الإدارة:
 `اعتماد الأولى إرجاع الثانية إبقاؤها رصيدًا ربطها بطلب آخر `  
# 16. ماذا لو دفع مبلغًا ناقصًا؟
 
مثلاً:
 `المطلوب = 50,000 المدفوع = 45,000 ` 
الحالة:
 `PARTIALLY_PAID Remaining = 5,000 ` 
ولا يتم اعتبار الطلب مكتمل الدفع.
  
# 17. ماذا لو دفع أكثر من المطلوب؟
 
مثلاً:
 `50,000 ` 
ووصل:
 `55,000 ` 
النظام يسجل:
 `Overpayment = 5,000 ` 
والإدارة تختار:
 `استرجاع رصيد عميل تطبيق على طلب آخر `  
# 18. بعد تأكيد الدفع
 
التدفق:
 `Payment Verified       ↓ Order Confirmed       ↓ Reserve Stock       ↓ Warehouse Processing       ↓ Packed       ↓ Ready For Shipping       ↓ Shipped       ↓ Out For Delivery       ↓ Delivered ` 
والعميل يرى الحالة مباشرة.
  
# 19. كود التتبع للعميل
 
مثلاً:
 `TRK-9X82LM ` 
العميل يستطيع إدخاله:
 `تتبع الطلب ` 
ويظهر:
 `تم استلام الطلب ✓ تم تأكيد الدفع ✓ تم تجهيز الطلب ✓ تم تسليمه لشركة الشحن ✓ خرج للتوصيل ✓ تم التسليم `  
# 20. ماذا يحدث إذا نفذ المنتج بعد الطلب؟
 
هنا يجب ألا يسمح النظام بأن يحدث:
 `عميل 1 اشترى آخر قطعة عميل 2 اشترى نفس القطعة ` 
يجب حجز المخزون.
 
مثلاً:
 `Available = 10 Reserved = 2 Sold = 5 ` 
والرصيد القابل للبيع:
 `10 - 2 - 5 = 3 `  
# 21. نظام المخزون
 
الإدارة لديها:
 `المنتجات الـ Variants المخازن الكميات الحركات المحجوز المباع التالف المرتجع ` 
كل حركة تسجل:
 `Stock Movement ` 
مثلاً:
 `+20 Purchase -2 Sale -1 Damage +1 Return ` 
وبهذا تستطيع معرفة لماذا أصبحت الكمية 18.
  
# 22. المستودعات
 
يمكن أن يكون هناك:
 `المخزن الرئيسي فرع 1 فرع 2 ` 
ويمكن نقل كمية:
 `Warehouse A → Warehouse B ` 
بحركة مخزون واضحة.
  
# 23. المشتريات
 
الإدارة تستطيع إدخال:
 `المورد الفاتورة الأصناف التكلفة الكمية الخصم المبلغ المدفوع المتبقي ` 
مثلاً:
 `Purchase Invoice Total = 2,500,000 Paid = 1,500,000 Remaining = 1,000,000 `  
# 24. حسابات الموردين
 
كل مورد له:
 `إجمالي مشتريات المدفوع المستحق المرتجع الرصيد آخر عملية `  
# 25. حسابات العملاء
 
العميل يمكن أن يكون له:
 `إجمالي الطلبات المدفوع المسترجع الرصيد النقاط المبالغ المستحقة ` 
وإذا أردت البيع الآجل لاحقًا:
 `Credit Order ` 
يصبح له كشف حساب.
  
# 26. النظام المحاسبي الداخلي
 
من المهم ألا يكون التطبيق فقط:
 
 
مبيعات + منتجات
 
 
بل يسجل الحركة المالية.
 
مثلاً عند بيع منتج:
 `Sale ↓ Cash/Bank Receivable ↓ Revenue ↓ Inventory Reduction ↓ Cost of Goods Sold ` 
وعند التحويل البنكي المقبول:
 `Bank Account ↑ Customer Payment ` 
وعند رد المبلغ:
 `Refund ↓ Bank/Cash decrease ` 
وهكذا تكون الأرقام مترابطة.
  
# 27. الحسابات البنكية داخل الإدارة
 
الإدارة تنشئ:
 `Bank Accounts ` 
مثلاً:
 `بنك A بنك B محفظة A محفظة B حساب آخر ` 
ولكل حساب:
 `الرصيد الافتتاحي الرصيد الحالي رقم الحساب حالة الحساب العملة الفرع اسم المستفيد `  
# 28. تسوية الحساب البنكي
 
الإدارة تدخل كشف البنك أو تتحقق يدويًا من التحويلات.
 
مثلاً:
 `System: PAY-7K4P29 = 25,000  Bank: 25,000 received ` 
فتصبح:
 `Reconciled ` 
ويمكن أيضًا تسجيل:
 `Bank Fee ` 
إذا كانت موجودة.
  
# 29. المرتجعات
 
العميل يضغط:
 `طلب إرجاع ` 
ويختار:
 `الطلب المنتج الكمية السبب صور ملاحظات ` 
ثم:
 `RETURN_REQUESTED ` 
الإدارة:
 `موافقة رفض مراجعة `  
# 30. الاستبدال
 
مثلاً:
 `M → L ` 
النظام يحسب الفرق:
 `New Price - Old Price = Difference ` 
إما:
 `العميل يدفع الفرق ` 
أو:
 `المتجر يعيد الفرق `  
# 31. إلغاء الطلب
 
الحالات:
 
### قبل الدفع
 
إلغاء مباشر.
 
### بعد الدفع وقبل التجهيز
 
إلغاء + Refund.
 
### بعد الشحن
 
حسب سياسة المتجر.
 
### بعد التسليم
 
تحول العملية إلى Return.
  
# 32. فشل التوصيل
 
مثلاً:
 `CUSTOMER_UNREACHABLE WRONG_ADDRESS CUSTOMER_REFUSED DELIVERY_FAILED ` 
وتستطيع الإدارة:
 `إعادة المحاولة إرجاع الطلب تغيير العنوان إعادة الجدولة `  
# 33. واتساب — بالطريقة التي تريدها
 
أنت لا تريد WhatsApp API.
 
ممتاز.
 
التطبيق يمكنه استخدام الانتقال المباشر إلى واتساب.
 
مثلاً:
 `تواصل معنا عبر واتساب ` 
يفتح:
 `WhatsApp ` 
مع رقم المتجر ورسالة مجهزة.
 
مثلاً:
 `مرحبًا، لدي استفسار بخصوص الطلب ORD-20260906-000125  كود التتبع: TRK-9X82LM ` 
ويمكن استخدام:
 `wa.me ` 
أو روابط واتساب المباشرة، بحسب المنصة.
 
لكن يجب فهم نقطة مهمة:
 
**التطبيق يستطيع فتح واتساب وإرسال المستخدم إلى المحادثة، لكنه بدون WhatsApp API لا يستطيع التحكم في رسائل واتساب نفسها أو استقبال الرسائل آليًا داخل النظام.**
 
إذًا سيكون التكامل:
 `App  ↓ Open WhatsApp  ↓ Customer chats with store ` 
وليس:
 `App  ↓ WhatsApp API  ↓ Automatic messaging engine `  
# 34. زر واتساب الذكي
 
يمكن أن يظهر في:
 
### المنتج
 `اسأل عن المنتج عبر واتساب ` 
الرسالة:
 `أريد الاستفسار عن: اسم المنتج SKU السعر ` 
### الطلب
 `استفسار عن طلبي ` 
ويتم تضمين:
 `رقم الطلب كود التتبع ` 
### الدفع
 `مشكلة في الدفع ` 
وتضمّن:
 `Payment Code Order Number `  
# 35. إدارة محتوى المتجر
 
هذه نقطة مهمة جدًا لأنك تريد التحكم الكامل.
 
الإدارة تستطيع من داخل التطبيق تعديل:
 `اسم المتجر الشعار البنرات الصور الألوان الصفحة الرئيسية التصنيفات المنتجات العروض سياسات المتجر الشحن الدفع رقم واتساب أرقام الهواتف الحسابات البنكية النصوص صفحات من نحن الأسئلة الشائعة شروط الاستخدام الخصوصية ` 
بدون إصدار جديد للتطبيق.
  
# 36. نظام Remote Configuration
 
هذا أحد أهم الأجزاء.
 
مثلاً:
 `{   "store_enabled": true,   "maintenance": false,   "orders_enabled": true,   "registration_enabled": true,   "bank_payment_enabled": true,   "whatsapp_enabled": true,   "minimum_version": "1.4.0" } ` 
الإدارة تستطيع التحكم في ذلك من التطبيق.
  
# 37. التحكم في تشغيل التطبيق
 
أنت طلبت:
 
 
الإيقاف والتشغيل
 
 
يجب أن يكون هناك:
 `STORE STATUS ` 
مثلاً:
 `ONLINE MAINTENANCE PAUSED ` 
عند الصيانة:
 `المتجر متوقف مؤقتًا للصيانة ` 
لكن يمكن السماح للمدير بالدخول.
  
# 38. إيقاف ميزة محددة فقط
 
بدلاً من إيقاف كل التطبيق:
 `Orders = OFF Payment = OFF Registration = ON Catalog = ON WhatsApp = ON ` 
مثلاً:
 
المتجر يعرض المنتجات ولكن يمنع الشراء مؤقتًا.
  
# 39. التحكم في الإصدارات
 
الإدارة تستطيع تحديد:
 `Current Version Minimum Version Latest Version ` 
مثلاً:
 `Latest = 2.0.0 Minimum = 1.8.0 ` 
إذا كان العميل على:
 `1.7.0 ` 
يمنع الدخول.
 
ويظهر:
 `يوجد إصدار جديد إلزامي. يرجى التحديث. ` 
أما:
 `1.9.0 ` 
فيعمل لكنه يظهر:
 `يوجد تحديث جديد `  
# 40. Kill Switch
 
وهذا مهم جدًا.
 
لو حدثت مشكلة خطيرة:
 `Emergency Shutdown = ON ` 
التطبيق يمنع العمليات الحساسة.
 
مثلاً:
 `عرض المنتجات = YES إضافة طلبات = NO الدفع = NO ` 
أو:
 `App Disabled ` 
وهذا يتم من السيرفر دون الحاجة لإعادة نشر التطبيق.
  
# 41. الإدارة لا تكون واجهة منفصلة بالضرورة
 
يمكن أن يكون التطبيق نفسه:
 `Customer App + Admin App ` 
لكن حسب صلاحية الدخول:
 `Customer → Store UI Admin → Admin UI ` 
والإدارة لا تظهر للمستخدم العادي.
 
مثلاً:
 `Role = ADMIN ` 
يظهر:
 `لوحة التحكم ` 
بينما:
 `Role = CUSTOMER ` 
يبقى في واجهة المتجر.
  
# 42. لوحة الإدارة الرئيسية
 
Dashboard:
 `مبيعات اليوم طلبات اليوم طلبات تنتظر الدفع طلبات تنتظر التجهيز طلبات قيد الشحن طلبات مكتملة إلغاءات مرتجعات عدد العملاء المخزون المنخفض صافي المبيعات ` 
مثلاً:
 `طلبات معلقة بالدفع: 17 طلبات تحتاج تجهيز: 8 طلبات بالشحن: 11 مرتجعات: 3 `  
# 43. مركز العمليات

# 112. أهم قرار معماري بالنسبة لمشروعك
 
أنا لا أنصح أن تبدأ المشروع كالتالي:
 `صفحة رئيسية صفحة منتجات سلة خلاص ` 
ثم بعد ذلك تحاول إضافة المحاسبة والدفع والمخزون.
 
الصحيح أن نبني **نواة البيانات والعمليات أولًا**:
 `Identity Catalog Inventory Order Payment Accounting Shipping Return Audit Configuration ` 
ثم نبني الواجهات فوقها.
 
لأن هذا هو الفرق بين تطبيق متجر بسيط وبين **منصة تجارية قابلة للتشغيل الفعلي**.
  
# 113. الشكل الذي أرى أنه الأنسب لمشروعك
 
**Flutter + Backend API + Relational Database + Object Storage + Remote Configuration + Role-Based Admin**
 
مع:
 `Offline Cache Repository Pattern Services Dependency Injection Central Error Handling Logging Audit Trail Arabic RTL Dark/Light Responsive UI Secure Authentication Server-side Validation Idempotent Operations Database Backup Export/Import Version Control Feature Flags ` 
وبهذه الطريقة تستطيع تشغيل المتجر في البداية بإمكانيات محدودة، ثم التوسع لاحقًا بدون إعادة بناء المشروع من الصفر.
 
**والأهم:** المتجر لا يكون مربوطًا بمنصة واحدة أو قاعدة بيانات واحدة بشكل يصعّب عليك الهجرة لاحقًا.
